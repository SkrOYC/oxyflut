## Codebase baseline

- **State today:** Stage 3 names Windows 11 25H2, Build Tools 17.14.39, SDK `10.0.26100.8876`, TSF and UI Automation families, per-output DXGI observation, and presentation acknowledgement, but leaves the Windows minimum, mappings, timing proof, recovery baseline, and immutable evidence open. The schema's evidence-object requirement means the cited fetches do not change those status fields until copies are committed.
- **Discovered constraints:** The official Windows release page identifies 25H2 as OS build 26200 and its GA base as 26200.6584. The SDK overview supports the 26100+ series but did not verify the pinned `10.0.26100.8876` installation. [S1] [S2]
- **Timing exclusion:** This report does not select or rely on `DwmGetCompositionTimingInfo` as a per-view opportunity source. `IDXGISwapChain::GetFrameStatistics` is also excluded because Microsoft documents it as unreliable in many multi-monitor scenarios. [S19]
- **Allocation symmetry:** Path A directly owns the documented candidate interfaces. Path B can satisfy the same contract only after its pinned fork proves an equivalent inventory and runs the same probes. Neither allocation receives credit for an unimplemented mapping.

## Options and trade-offs

- **Option A:** Use a scheduler-owned, per-window `IDXGISwapChain2::GetFrameLatencyWaitableObject` stream and a separate harness-owned `IDXGIOutput::WaitForVBlank` meter on the same output, then use a separately selected acknowledgement path only after controlled correlation, noninterference, and migration tests pass.
- **Option B:** Evaluate only the documented acknowledgement alternatives: `DCompositionWaitForCompositorClock` with `IDCompositionDevice::GetFrameStatistics`, or the Windows 11 Composition Swapchain `IPresentationManager` present-statistics queue with `IPresentStatistics` and `IPresentationBuffer::IsAvailable`.
- **Option C:** Retain timing, acknowledgement, recovery, mapping, source-snapshot, and host-installation rows as gating KUs whenever the required immutable source copy, API attribution, host approval, or controlled trace is absent.
- **Build and API choice:** Select the 25H2 GA build and the documented Win32, TSF, UI Automation, topology, and device-loss interfaces. Retain the exact installed SDK version as a KU until a Windows-host capture provides its identity and digests.
- **Accessibility choice:** Use the server-side provider interfaces in the focused baseline and require the integrated allocation to enumerate a matching path. Retain complete maps and Narrator behavior as KUs until both candidates produce map evidence.
- **Recovery choice:** Use `ChangeDisplaySettingsExW` only for controlled topology or mode tests. It does not prove surface-loss or graphics-device-loss injection.

## Recommendation

- **Chosen option:** Use a mix: A for B002-WIN-01, B002-WIN-03, B002-WIN-04, B002-WIN-07, B002-WIN-10, B002-WIN-13, and B002-WIN-14 after their source snapshots are committed; B for the finite B002-WIN-11 acknowledgement selection; A with C as the gating fallback for B002-WIN-15; and C for B002-WIN-02, B002-WIN-05, B002-WIN-06, B002-WIN-08, B002-WIN-09, B002-WIN-12, and B002-WIN-16. - **Why it fits:** The direct allocation has a concrete vendor-documented candidate surface without asserting candidate results. The integrated allocation is held to that same surface and evidence suite. The retained KUs prevent an unreliable multi-monitor statistic, a candidate counter, or an inferred default HWND from weakening CAP-VIEW-004, CAP-SEM-001, CAP-SEM-002, CAP-IME-001, CON-FRM-001, or the recovery constraints.

### B002-WIN-10 two-stream, two-display procedure

Use a physical Windows host with two occupied outputs at different refresh rates. On each output, place one noncandidate HWND flip-model swap chain created with `DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT`. The scheduler worker owns that window's `IDXGISwapChain2::GetFrameLatencyWaitableObject` handle and waits with `WaitForSingleObject`; the independent harness worker owns a distinct `IDXGIOutput::WaitForVBlank` call against the same current `IDXGIOutput`. Do not use the meter for scheduling, and do not use the scheduler stream as a meter. [S16] [S17] [S18] [S27] [S40] [S41]

For every return, record a JSON record with `role` (`scheduler-opportunity` or `harness-meter`), QPC timestamp and frequency, `HWND`, swap-chain identity, `HMONITOR`, output epoch, worker identity, HRESULT or wait result, and interval from that role's previous record. Capture a 10-second meter-only baseline, then a 10-second two-stream co-run for both displays. Compare within-output stream correlation and interval distributions, and compare scheduler records between the meter-only control and co-run to detect added or missing opportunities or changed cadence. Move one HWND to the other output, resolve `GetContainingOutput` again, start a new epoch, and prove that both role-tagged streams rebind to the new `HMONITOR` while the untouched output retains its own cadence. Preserve the raw trace and a derived correlation, interference, and migration summary. This procedure has no selected result yet.

### B002-WIN-15 fault-injection procedure

Primary mechanism: on an approved physical Windows host, query the actual candidate test device for `ID3D12Device5`, record the QPC timestamp, call `RemoveDevice`, then record the first `Present` HRESULT and the device-removed reason before any recovery state changes. Microsoft documents that `RemoveDevice` tells the Direct3D 12 runtime that the device can no longer be used and signals monitored fences; this probe must still prove the candidate-visible DXGI result. [S20] [S24] [S33]

Fallback one: only with written host-owner approval, invoke `pnputil /restart-device "GPU_INSTANCE_ID"` for the selected GPU and preserve command output, device instance ID, operator approval, external timestamp, and recovery trace. Microsoft documents `pnputil /restart-device` as the replacement for `devcon restart`; this report neither selects DevManView nor assumes that a device restart is host-approved. [S34]

Fallback two: only in an approved driver-development test session, run the WHLK SimulatePreemption TDR test. Microsoft's TDR documentation says that WHLK provides that manual trigger and that `TdrDelay` and related registry keys are for driver-development testing only; it also says applications must not manipulate them outside targeted testing or debugging. Do not substitute an undocumented long-running shader. [S35] [S36]

For any mechanism, preserve the exact fault recipe, host approval, external fault timestamp, `Present` HRESULT, `GetDeviceRemovedReason` result, recreation-attempt count, superseded-resource release timestamps, and first acknowledged recovered frame. If `QueryInterface(ID3D12Device5)` fails, a fallback lacks approval, or the fault does not produce a candidate-visible removal or reset, stop that mechanism and retain B002-WIN-15 as a gating KU. Surface-loss evidence remains separately required.
