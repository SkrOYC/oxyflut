### B002-WIN-10 two-stream, two-display procedure

Use a physical Windows host with two or more occupied outputs at different refresh rates. Create one noncandidate `HWND` per occupied output and create its flip-model swap chain with `IDXGIFactory2::CreateSwapChainForHwnd`. Freeze `DXGI_SWAP_CHAIN_DESC1` to `BufferCount=2`, `Format=DXGI_FORMAT_B8G8R8A8_UNORM`, `SampleDesc.Count=1`, `SampleDesc.Quality=0`, `BufferUsage=DXGI_USAGE_RENDER_TARGET_OUTPUT`, `SwapEffect=DXGI_SWAP_EFFECT_FLIP_DISCARD`, and `Flags=DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT`. Do not include `DXGI_SWAP_CHAIN_FLAG_ALLOW_TEARING`. `DXGI_SWAP_CHAIN_DESC1` owns the swap-chain fields, and `DXGI_SWAP_EFFECT_FLIP_DISCARD` is a flip-model value. [S50] [S51] [S61]

After obtaining `IDXGISwapChain2`, call `SetMaximumFrameLatency(1)` and record its `HRESULT`. Abort the output epoch unless it returns `S_OK`. Get the frame-latency handle with `GetFrameLatencyWaitableObject`, and record that handle as the scheduler identity. Microsoft requires the waitable-object creation flag for that method, and makes `SetMaximumFrameLatency` valid only on a waitable-object swap chain. Obtain the QPC frequency once with `QueryPerformanceFrequency`; record every QPC observation with that frequency. [S27] [S40] [S49] [S64]

Set `continuousInvalidation=true` before each measured phase and keep it true for the complete phase. The scheduler must not wait for `WM_PAINT` or an application invalidation. Its complete per-frame loop is: wait on the frame-latency handle with `WaitForSingleObject(handle, 100)`; record the wait result; on `WAIT_OBJECT_0`, record the opportunity QPC timestamp before rendering; clear the acquired render target to a solid deterministic RGBA color derived from monotonically increasing `frameId`; call `IDXGISwapChain::Present(1, 0)`; and record `frameId`, the clear color, the QPC submission timestamp, and the returned `HRESULT`. The clear gives every submitted frame deterministic content, while `frameId` identifies it in the trace. A timeout records no opportunity and lets shutdown check the stop flag. `Present` with sync interval 1 synchronizes to one vertical blank in the flip model. [S20] [S41] [S62]

The harness meter is a separate worker that repeatedly calls `IDXGIOutput::WaitForVBlank` against the output in the scheduler's active epoch. After each successful return, it records its QPC timestamp. The meter never writes scheduler state, decides an invalidation, or calls `Present`. `WaitForVBlank` blocks until vertical blank; the scheduler's waitable-object signal is a separate stream. [S16] [S27]

Determine the active mode before every phase and after every topology or window-output change. First call `GetContainingOutput`, then read `DXGI_OUTPUT_DESC.Monitor` to obtain the scheduler's `HMONITOR`. Pass that monitor to `GetMonitorInfoW` with `MONITORINFOEXW` and record `szDevice`. Size the arrays with `GetDisplayConfigBufferSizes`, then call `QueryDisplayConfig(QDC_ONLY_ACTIVE_PATHS | QDC_VIRTUAL_MODE_AWARE | QDC_VIRTUAL_REFRESH_RATE_AWARE)`. For every active path, request `DISPLAYCONFIG_SOURCE_DEVICE_NAME` through `DisplayConfigGetDeviceInfo`, using that path's source adapter LUID and source ID. Match `viewGdiDeviceName` exactly, case-insensitively, to `MONITORINFOEXW.szDevice`. Reject an epoch if zero or multiple active paths match. [S17] [S18] [S53] [S58] [S59] [S60] [S65]

For the one matched path, record the source adapter LUID and ID, target adapter LUID and ID, `targetInfo.refreshRate`, and every indexed `DISPLAYCONFIG_MODE_INFO`. If `DISPLAYCONFIG_PATH_SUPPORT_VIRTUAL_MODE` is set, select `targetModeInfoIdx`; otherwise select `modeInfoIdx`. The selected mode entry must have `infoType=DISPLAYCONFIG_MODE_INFO_TYPE_TARGET` and matching target adapter LUID and ID. When that entry is available, use its `targetMode.targetVideoSignalInfo.vSyncFreq` as the active period `T`; otherwise use `targetInfo.refreshRate`. Reject the epoch if the selected rational has a zero numerator or denominator. When both rationals are available, reject the epoch if their refresh frequencies differ by more than 0.1%. The path structure owns `targetInfo`; the target structure identifies the refresh rational and target mode; the mode table identifies a target entry; and the video-signal structure defines `vSyncFreq`. This replaces `IDXGIOutput::GetDisplayModeList`, which enumerates supported modes and does not identify the active mode. [S53] [S54] [S55] [S56] [S57]

Define an output epoch as the tuple of `HMONITOR`, `szDevice`, source adapter LUID and ID, target adapter LUID and ID, selected refresh rational, `DISPLAYCONFIG_PATH_BOOST_REFRESH_RATE` state, and the QPC timestamp of the display-configuration query. End the epoch before processing a record whose tuple differs. Start a new epoch only after the mapping succeeds again. During a window move, both workers must stop their prior epoch, resolve the new tuple, and then resume. Unmoved outputs must retain their epoch and scheduler cadence. [S17] [S18] [S53] [S54] [S58] [S59] [S60]

Freeze the variable-refresh policy to the no-tearing path: the swap-chain flags contain only `DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT`, and every frame uses `Present(1, 0)`. `DXGI_PRESENT_ALLOW_TEARING` requires sync interval 0, so this loop cannot use that flag. Record `DISPLAYCONFIG_PATH_BOOST_REFRESH_RATE` from the active path and retain B002-WIN-10-VRR as a separate gate for graphics-driver and panel state. If the boost flag is set, retain its trace but exclude its epoch from the B002-WIN-10 pass calculation. [S20] [S52] [S53] [S54]

For every scheduler and meter record, preserve `role`, QPC timestamp and frequency, `HWND`, swap-chain identity, `HMONITOR`, output epoch, worker identity, wait result or `HRESULT`, `frameId` when applicable, and the interval from the same role's preceding record. For every output, capture a 10-second settled scheduler-only baseline, then a 10-second settled two-stream co-run. An optional 10-second meter-only phase can characterize the meter, but cannot control the scheduler noninterference comparison.

For the scheduler stream in each output and phase, calculate count, minimum, p50, p95, p99, maximum, `sum(max(0, round(interval / T) - 1))` for intervals at least `1.5T`, and `abs(mean(interval) - T) / T`. In the co-run only, greedily pair timestamp-ordered scheduler opportunities and meter events one-to-one when their absolute QPC time difference is at most `T / 4`. Let `P` be the paired count, `Ns` the eligible scheduler count, and `Nm` the eligible meter count. Calculate the Pearson correlation coefficient `r` from the paired scheduler and meter timestamps after subtracting the first paired timestamp from each series. Calculate `missedPairRate = (max(Ns, Nm) - P) / max(Ns, Nm)`. Require `r >= 0.99` and `missedPairRate <= 0.001` on every occupied output. Fail the output if either condition fails, a required successful `Present` record is missing, or the active-mode mapping fails.

The meter is noninterfering only when every occupied output has no additional missed-vsyncs in the co-run, an absolute co-run-to-baseline drift difference no greater than 0.01, and p50, p95, and p99 differences no greater than `0.1T`. Move one `HWND` to another output and prove both role-tagged streams use the new epoch while untouched outputs retain cadence. Preserve raw traces and the active-mode, correlation, missed-pair, noninterference, variable-refresh, and migration summaries. If any pass condition fails, stop that output's row and retain B002-WIN-10 as a gating KU.

At phase end, clear `continuousInvalidation`, set the stop flag, wait for each worker to exit before releasing its Direct3D and DXGI objects, and close the waitable handle exactly once with `CloseHandle`. Never close the handle while a worker is waiting on it. `GetFrameLatencyWaitableObject` requires callers to close its returned handle when finished. [S27] [S63]

### B002-WIN-15 fault-injection procedure

Primary mechanism: on an approved physical Windows host, query the actual candidate test device for `ID3D12Device5`, record the QPC timestamp, call `RemoveDevice`, then record the first `Present` HRESULT and the device-removed reason before any recovery state changes. Microsoft documents that `RemoveDevice` makes the device unusable and signals monitored fences; this probe must still prove the candidate-visible DXGI result. [S20] [S24] [S33]

Fallback one: only with written host-owner approval, invoke `pnputil /restart-device` for the selected GPU and preserve the exact device instance ID, command output, operator approval, external timestamp, and recovery trace. Microsoft documents `pnputil /restart-device` as the replacement for `devcon restart`. [S34]

Fallback two: only in an approved driver-development test session, run the WHLK SimulatePreemption TDR test. Microsoft's TDR documentation says that WHLK provides that manual trigger and that `TdrDelay` and related registry keys are for driver-development testing only. Do not substitute an undocumented long-running shader. [S35] [S36]

For any mechanism, preserve the exact fault recipe, host approval, external fault timestamp, `Present` HRESULT, `GetDeviceRemovedReason` result, recreation-attempt count, superseded-resource release timestamps, and first acknowledged recovered frame. If `QueryInterface(ID3D12Device5)` fails, a fallback lacks approval, or the fault does not produce a candidate-visible removal or reset, stop that mechanism and retain B002-WIN-15 as a gating KU. Surface-loss evidence remains separately required.
