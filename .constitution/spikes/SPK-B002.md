## Context and objective

- **Triggering upstream file or section:** `.constitution/tech-spec/contracts/platform-contracts.json` -> `environments.windows`
- **Target:** Replace each Windows `ku-gating` item with cited KK evidence or a smaller named blocker.
- **Archetype / surface:** Library/SDK with System/Native Windows integration.
- **Status interpretation:** KK applies only to the precise interface or released build named in its row. It does not promote either allocation, certify a candidate behavior, or close a neighboring KU.

## Codebase baseline

- **State today:** Stage 3 names Windows 11 25H2, Build Tools 17.14.39, SDK `10.0.26100.8876`, TSF and UI Automation families, per-output DXGI observation, and presentation acknowledgement, but leaves the Windows minimum, mappings, timing proof, recovery baseline, and immutable evidence open.
- **Discovered constraints:** The official Windows release page identifies 25H2 as OS build 26200 and its GA base as 26200.6584. The SDK overview supports the 26100+ series but did not verify the pinned `10.0.26100.8876` installation. [S1] [S2]
- **Timing exclusion:** This report does not select or rely on `DwmGetCompositionTimingInfo` as a per-view opportunity source. `IDXGISwapChain::GetFrameStatistics` is also excluded because Microsoft documents it as unreliable in many multi-monitor scenarios. [S19]
- **Allocation symmetry:** Path A directly owns the KK interfaces. Path B can satisfy the same contract only after its pinned fork proves an equivalent inventory and runs the same probes. Neither allocation receives credit for an unimplemented mapping.

## Options and trade-offs

- **Option A:** Use `IDXGIOutput::WaitForVBlank` per output plus a separate presentation-acknowledgement path when controlled tests prove independence and migration behavior.
- **Option B:** Select another official per-output timing mechanism with equal external observability and tighter variable-refresh support.
- **Option C:** Retain timing or recovery rows as gating KUs when neither mechanism supplies externally attributable evidence.
- **Build and API choice:** Select the 25H2 GA build and the documented Win32, TSF, UI Automation, topology, and device-loss interfaces. Retain the exact installed SDK version as a KU until a Windows-host capture provides its identity and digests.
- **Accessibility choice:** Use the server-side provider interfaces in the focused baseline and require the integrated allocation to enumerate a matching path. Retain complete maps and Narrator behavior as KUs until both candidates produce map evidence.
- **Recovery choice:** Use `ChangeDisplaySettingsExW` only for controlled topology or mode tests. It does not prove surface-loss or graphics-device-loss injection.

## Recommendation

- **Chosen option:** Use a mix: A for the documented interface baselines and controlled topology injection; C for timing independence, presentation acknowledgement, candidate mappings, multi-view routing, exact SDK installation, and surface or graphics-device-loss injection.
- **Why it fits:** The direct allocation has a concrete vendor-documented surface without asserting candidate results. The integrated allocation is held to that same surface and evidence suite. The retained KUs prevent an unreliable multi-monitor statistic, a candidate counter, or an inferred default HWND from weakening CAP-VIEW-004, CAP-SEM-001, CAP-SEM-002, CAP-IME-001, or the recovery constraints.
- **Rejected options:** Reject global DWM timing, `IDXGISwapChain::GetFrameStatistics` as a multi-monitor acknowledgement, undocumented COM behavior, candidate-only counters, implicit HWND selection, and UI Automation property substitution for a complete map.
- **Qualification effect:** Windows remains `ku-gating`; neither allocation is eligible to collect scored qualification evidence from this spike alone.
